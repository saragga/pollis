# 3.2 Semantic review of the code examples, batch 7

Task 3.2 of the Pollis Polish Roadmap. Batch 7 is files 145 to 168 of `LC_ALL=C ls src/vs/workbench/contrib/model/browser/webviews/*.toml`, from `novd` to `rng`. All 24 panels were reviewed.

The code was read as `node build/pollis/extractCodeExamples.ts` renders it (`.build/code-examples/<id>/<model>.jl`), covering the default code of every model and every Next Steps action, with each input at its default. No Julia was run; task 3.4 runs the code. Wikis and notebooks are out of scope. Verdicts, finding ratings and the "fixed" rule follow the batch 1 report (`3.2-semantic-review-batch-1.md`). A panel with a finding rated wrong is rated at least questionable, even when that finding is fixed here. A breach of the TOML house rules (such as non-ASCII in code) is marked "Rule violation" and does not lower the scientific verdict.

Where a finding depends on a package's API, I checked the package's exports or README on GitHub (PEtab.jl, PortfolioOptimisers.jl), and each such finding says so. Items already tracked elsewhere are not repeated: postfix transposes, `bert` token attribution, `rl` Zygote, the `kgds`/`diff` mentions and `rxinfer`'s `gaussian_model`. The `rl` here is the Recurrent Layers panel, and its Flux branch's use of Zygote is that tracked item.

## Cross-cutting findings

- **T1. Package APIs that do not exist or have moved.** This is the largest problem in the batch, and none of it can be fixed locally.
  - `ode` is written against PEtab.jl functions that are not exported (checked against its export list).
  - `po` uses the retired API of PortfolioOptimiser.jl under the new package's name (checked against the PortfolioOptimisers README).
  - `rctl` and `rdyn` mix RobotDynamics.jl with RigidBodyDynamics.jl and call methods neither package has.
  - `ptp` and `ptps` could not be matched to HawkesProcesses.jl or PointProcesses.jl.

  Task 3.4 will confirm this quickly; each panel needs a rewrite against the current API.
- **T2. Defaults that switch the feature off.** This is the same pattern as U1 in batch 6.
  - `pgo`'s search box was centred on the Rastrigin optimum, so every method found it at its first evaluation (fixed).
  - `qn` compares L-BFGS memory sizes in 2 dimensions, where the memory never binds.
  - `rcme`'s default shrinkage target did not match the data's scale (fixed).
- **T3. Actions that ignore the selected model.**
  - `ppl`'s predictive check called `gaussian_model` in every branch (fixed).
  - `ptp`/`ptps` use `process` and Hawkes parameters in every branch.
  - `po` optimises mean-variance whatever the model.
- **T4. Arguments in the wrong order.** GaussianProcesses kernels take (log length scale, log sigma), but `ptp` and `ptps` passed (log variance, log length scale) (fixed).
- **T5. In-sample checks.** `po` compares Sharpe ratios in-sample, where minimum variance wins by construction. `ptp`'s time-rescaling KS test uses parameters fitted to the same events, so its p-value is conservative.
- **T6. Non-ASCII in code.**
  - `nscr` had `é` escapes inside `'''` strings, which compile-toml decodes (fixed).
  - `qrng` has a `×` in seven comments.

  Only the escapes were fixed; comments are left for task 3.3.

## Panel reviews

### novd: Novelty Detection

**Sound, rich.** Three detectors:
- a two-sided standardised CUSUM (k = 0.5, h = 5, for an in-control ARL0 of about 465, which the false-alarm action checks by simulation);
- a Gaussian Mahalanobis detector with a chi-square(p) threshold;
- a one-class SVM on standardised features.

Actions include the monitoring plot, false-alarm rates against their nominal values, online monitoring, the CUSUM (k, h) trade-off, agreement between the OC-SVM and Gaussian detectors, and what changed.

1. **Questionable. Action `explain-novelty`.** It measures the shift from the alarm onwards, but CUSUM alarms after a delay. The change-point estimate is the last time the alarming statistic was 0 before the alarm.
2. **Questionable. Model `gauss`.** The chi-square threshold treats the estimated mean and covariance as known and assumes normality. With n training points, the exact law is a scaled F.
3. **Questionable. Action `online-monitor`.** It hard-codes 0.5 and 5 instead of k and h.

### nscr: Net Survival & Competing Risks

**Sound, rich.** Net survival with NetSurvival.jl against a population rate table. Models include Pohar-Perme net survival with a band, Cronin-Feuer crude mortality (disease against other causes) and the Graffeo test. Actions show excess, expected and observed hazards, a cohort summary, a check for negative excess hazard, milestones, and Pohar-Perme against Ederer I, Ederer II and Hakulinen (with the reason the older estimators are biased), plus a plain-language summary. The estimators' Unicode field names are built from `Char` codes, so the code stays ASCII.

1. **Rule violation, fixed (`04e3331c`).** Two code lines wrote `Grafféo` with a `\u` escape inside a `'''` string, which compile-toml decodes to a non-ASCII character.
2. **Questionable. Action `relative`.** "Observed" survival is built from Pohar-Perme's hazard increments, which are weighted by inverse expected survival. So So is not the Kaplan-Meier observed survival, and So/Sp is not the classical relative survival.
3. **Questionable. Action `covariates`.** It runs one Graffeo test per column and ranks the p-values with no multiple-testing adjustment.
4. **Questionable.** `confint(est; level=0.05)` is commented "95%"; check whether NetSurvival's `level` is alpha or coverage.

### oa: Online Algorithms

**Sound, thin.** A tour of OnlineStats: Mean, Variance, Extrema, Hist, LinReg, P2Quantile, merge and windowing.

1. **Questionable. Action `compare-batch`.** It checks Mean and Variance, which are exact up to rounding. The approximate estimators (P2Quantile, Hist) are never compared with exact quantiles.
2. **Questionable. Action `stream-predict`.** It collects predictions but never scores them.
3. **Questionable. Action `predict-linreg`.** `x_new = [1.0, 2.0]` ignores `size(X, 2)`, and the comment assumes an intercept column that LinReg does not add.
4. **Questionable.** `WindowMean` may not be an OnlineStats type (`MovingWindow` is), and `Kurtosis` reports excess kurtosis while the comment says "fourth standardised moment"; both need checking.

**Proposal (thin).** The panel should answer: what does a single pass cost in accuracy, and how do online estimators follow a process that changes? Stream a simulated series with a level shift halfway, and compare:
- P2Quantile and Hist against exact quantiles as n grows;
- equal weighting against `ExponentialWeight` and a moving window in tracking the shift;
- the prequential error (predict, then update) of LinReg against a batch refit.

Add memory use against n to show the point of streaming.

### pbm: Pareto-Based Multi-Objective Optimisation

**Sound, rich.** Binh-Korn, a constrained bi-objective problem (objectives, constraints and bounds checked), solved with NSGA-II, NSGA-III, SPEA2 and SMS-EMOA. Actions include hypervolume convergence, spacing and feasibility, hypervolume spread over 5 seeds, budget sensitivity, the trade-off rate along the front, a common-reference comparison, IGD against the non-dominated union, the Pareto set and a compromise solution.

2. **Questionable. Action `knee`.** The "Knee Point" is the point nearest the ideal point after scaling. That is a compromise solution, not a knee; rename it or compute the knee.

### pdes: Partial Differential Equations

**Sound, rich.** The method of lines for the heat and wave equations (Dirichlet, Neumann or periodic boundaries) and the five-point Poisson problem (direct or CG). Actions include:

### pgm: Policy Gradient Methods

**Sound, rich.** Policy gradients written out on CartPole; I checked the Gym dynamics term by term. The policy is linear-softmax, with a least-squares quadratic critic as the baseline. Three updates are implemented:
- REINFORCE;
- PPO (the gradient of the clipped surrogate is correct);

Actions include entropy, gradient norms, KL per update, five seeds, greedy against stochastic returns, a batch-size study and the policy map.

No findings of substance. The comparison of the three methods uses one seed.

### pgo: Principled Global Search with Local Refinement

**Questionable, rich.** 2-D Rastrigin with NLopt's AGS, MLSL (low-discrepancy sampling plus BOBYQA) and randomised StoGO, with every evaluation recorded. Actions include the landscape, the best-so-far curve, the return code, seed robustness, an L-BFGS polish, five methods over 3 seeds, and a budget study.

### po: Portfolio Optimisation

**Wrong, adequate.** Mean-variance, mean-CVaR, HRP and HERC portfolios.

1. **Wrong, not local (T1).** The code loads PortfolioOptimisers but uses the retired API of PortfolioOptimiser.jl: `Portfolio(; returns)`, `optimise!(port, Trad(...))` and `port.weights`. According to the PortfolioOptimisers README, the current API is `MeanRisk(; opt = JuMPOptimiser(...))`, `optimise(mr, rd)` and `res.w`. `efficient_frontier!`, `risk_contribution(port)` and `rolling_sharpe` could not be found either.
2. **Questionable (T3). All actions.** Every action optimises `Trad(rm = Variance())`, whatever the model.
3. **Questionable (T5). Actions `compare-equal-weight` and `compare-methods`.** They compare Sharpe ratios in-sample, where the minimum-variance portfolio wins on variance by construction. The out-of-sample action exists, but these comparisons do not use it.
4. **Questionable.** Sharpe ratios ignore the risk-free rate, and are annualised with 252 in some actions but not others (daily data is assumed and never stated). `mean` and `std` are used without `Statistics`. The frontier's "Sharpe-optimal portfolio" is never located. A single 50/50 split is a weak out-of-sample test.

### ptp: Point Processes

**Wrong, adequate.** Estimation for Poisson, inhomogeneous (KDE), Hawkes, network Hawkes and log-Gaussian Cox processes. Actions include time-rescaling KS and Q-Q, the branching ratio, forecasting, AIC/BIC and the immigrant/offspring split.

1. **Wrong, fixed (`968eb3c4`). Model `cox` (T4).** GaussianProcesses' `SEIso`, `Mat32Iso` and `Mat52Iso` take (log length scale, log signal sd). The code passed (log variance, log length scale), so the defaults meant a length scale of 1 and a log-intensity sd of 10 (intensities spanning e^+-20) instead of length 10 and variance 1.
2. **Wrong, fixed (same commit). Actions `branching-ratio` and `branching-interpret`.** They printed the input values as "fitted parameters". The Hawkes model now reads its fit, and other models label the values as inputs.
3. **Questionable (T1).** The APIs could not be matched to HawkesProcesses.jl or PointProcesses.jl (which has no `CoxProcess`). `intensity`, `cumulative_intensity`, `next_event`, `simulate(...; history)` and `weight_matrix` are unverified.
4. **Questionable (T3).** Most actions use `process`, which only the two Hawkes branches define.
5. **Questionable.** The KS time-rescaling test uses parameters fitted to the same events, so its p-value is conservative. The KDE intensity is biased down near 0 and T. The Poisson interval is Wald; the exact interval is better for small counts.

### ptps: Point Process Simulation

**Wrong, thin.** Simulation of the same five processes. The inhomogeneous model uses Lewis-Shedler thinning with lambda(t) = 1 + sin(t/10) <= 2, which is correct.

1. **Wrong, fixed (`ae060858`) (T4).** The same kernel argument order as in `ptp`.
2. **Wrong, not local (T3).** Count-against-theory compares with lambda T = 100, and the KS test with Exponential(1), for every model. For Hawkes, E[N(T)] is about mu T/(1 - rho) = 60 here, and inter-event times are over-dispersed. For the inhomogeneous model, E[N] is the integral of lambda. `process` is undefined for the inhomogeneous and Cox models.
3. **Questionable (T1).** The API is unverified, as in `ptp`.

**Proposal (thin).** The panel should answer: how do clustering and time variation change what we see compared with a Poisson process of the same mean rate? Simulate a Poisson, an inhomogeneous and a Hawkes process with the same expected count over [0, T], and compare:
- counts per window (the variance-to-mean ratio: 1 for Poisson, above 1 for the others);
- the inter-event time distribution against Exp;
- the time-rescaling transform under each process's own true intensity, which should give Exp(1) in every case.

For Hawkes, check E[N(T)] = mu T/(1 - rho) by simulation, and show what happens as rho approaches 1.

### ql: Q-Learning

**Sound, rich.** Cliff Walking (-1 per step; -100 and back to the start at the cliff; optimal return -13, correct) solved by tabular Q-learning and SARSA, and by DQN with replay and a target network. Actions include the learning curve, the value heatmap, TD error, seeds, the greedy path, greedy against epsilon-greedy returns, Q-learning against SARSA (the classic safe-path result), and an epsilon sweep.

1. **Questionable.** The DQN uses `Flux.withgradient` (Zygote). The exploration sweep compares training returns, which penalise exploration by construction; the greedy return next to it is the fair measure.

### qn: Quasi-Newton Methods

**Sound, adequate.** BFGS and L-BFGS on 2-D Rosenbrock. Actions include traces, successive error ratios (superlinear), the local quadratic model, and comparisons of methods and line searches.

1. **Questionable (T2).** In 2 dimensions, L-BFGS with m = 10 or 20 stores more pairs than there are dimensions, so BFGS and L-BFGS behave the same and the memory comparison shows nothing. The case for L-BFGS (O(mn) memory against O(n^2)) needs n in the hundreds, for example the extended Rosenbrock with n = 1000. The panel also duplicates much of `optim`.

### qp: Quadratic Programming

**Sound, rich.** Markowitz portfolios on plausible annual figures (returns of 7-15%, volatility about 25%):
- a QP (minimum variance for a target return);
- a QCQP (maximum return under a volatility cap);
- an MIQP with a cardinality limit.

Actions include the frontier, a convexity check, duals and reduced costs (with the selection fixed for the MIQP), sweeps, solver comparisons, equal-weight and global-minimum-variance benchmarks with the relaxation bound, shadow prices with correct units, and variance attribution.

1. **Questionable.** The QCQP grid starts below the long-only minimum-variance volatility, so its first points are infeasible and appear as unexplained gaps. Expected returns are treated as known, with no estimation error or out-of-sample check (the usual failure of mean-variance).

### rcme: Robust Covariance Matrix Estimation

**Questionable, rich.** Ledoit-Wolf linear, OAS and analytical nonlinear shrinkage on a simulated 3-factor covariance (40 assets, 60 observations), so the truth is known. Actions include the spectrum against the truth, conditioning, shrinkage intensity recovered by projection (correct), minimum-variance portfolios in and out of sample, each estimator's Frobenius error, and partial correlations.

1. **Wrong, fixed (`13a6fc68`). Input `target` (T2).** The `lw` default target was `DiagonalUnitVariance` (the identity), which the tooltip called the scaled identity. With variances of about 0.35, it pulls every variance towards 1. The default is now `DiagonalCommonVariance`, the Ledoit-Wolf (2004) target, and the tooltip is corrected.
2. **Questionable. Action `out-of-sample`.** It estimates on 30 observations of 40 assets, where the sample covariance is singular and `pinv` gives the minimum-norm solution; say so. There is one split and no repetition.

### rctl: Robot Control

**Wrong, thin.** Control laws (PD with gravity compensation, computed torque, Jacobian-pseudoinverse IK, Cartesian impedance) given as fragments.

1. **Wrong, not fixed.** Every Jacobian is `Matrix(geometric_jacobian(state, path))[1:3, :]`. RigidBodyDynamics stacks the angular part first, so these rows map joint rates to angular velocity, not end-effector position. The linear rows of a twist Jacobian are not the end-effector point velocity either; `point_jacobian` gives that. IK, impedance, rank and manipulability all use the wrong matrix. The fix belongs in the rewrite, because the surrounding code does not run (next point).
2. **Wrong, not local (T1).** The panel mixes RobotDynamics.jl, a trajectory-optimisation package, with RigidBodyDynamics.jl. `RobotDynamics.nv`, `inverse_dynamics(mechanism, q, v, a)`, `gravity_compensation`, `dynamics(mechanism, x, u)` and `transform(state, ee_body, root_body)` are not RigidBodyDynamics methods; its forms are `inverse_dynamics(state, vd)` and `dynamics!(result, state, tau)`. The mechanism, gains, targets and histories are all undefined.
3. **Questionable. Action `pd-vs-ct`.** It compares torques at one state instead of tracking over a trajectory.

**Proposal (thin).** The panel should answer: how much does model-based control (computed torque) gain over PD with gravity compensation when tracking a fast trajectory, and what happens when the model is wrong? Load a two-link arm from a URDF shipped with the panel, or `rand_chain_mechanism`, and simulate both controllers with `RigidBodyDynamics.simulate` on a sinusoidal joint reference. Plot the tracking errors, then repeat with 20% payload mismatch. Compute IK with `point_jacobian` and damped least squares near singularities, and report manipulability along the path.

### rdyn: Robot Dynamics

**Wrong, thin.** Dynamics, kinematics and rotations given as fragments.

1. **Wrong, fixed (`54f986ce`). Action `rotation-viz`.** `R_mat .* basis` broadcast the matrix against a vector of vectors element by element; it is now `[R_mat * b for b in basis]`.
2. **Wrong, not local (T1).** As in `rctl`, it mixes RobotDynamics.jl and RigidBodyDynamics.jl, uses non-existent signatures, and has undefined `model`, `mechanism`, `x`, `u`, `q`, `v`, `a` and `R`.
3. **Questionable.** `dynamics-check` and `fd-vs-id` are the same round trip. `ee-trajectory` only fits a one-joint robot. `SVector` needs StaticArrays. `q_dot = xdot[1:nv]` fails for quaternion joints (nq != nv).

**Proposal (thin).** The panel should answer: what do forward and inverse dynamics say about a real arm? For example: which torques hold it against gravity, and how the mass matrix, and so the effort needed, changes with configuration. Use RigidBodyDynamics only, on a shipped two- or three-link URDF. Compute:
- `mass_matrix` and its condition number over a grid of configurations;
- gravity torques from `inverse_dynamics` with zero velocity and acceleration;
- a free-fall simulation with an energy-conservation check;
- the forward-inverse round trip as a test.

Keep the rotations part as a separate, runnable section on quaternion drift and renormalisation.

### rl: Recurrent Layers

**Questionable, thin.** MGU and about twenty other recurrent cells in Flux (RecurrentLayers.jl) and Lux (LuxRecurrentLayers.jl). Actions include a hidden-state heatmap, predictions, parameter counts, gradient norms, validation loss, size against LSTM/GRU, and input sensitivity.

1. **Wrong, fixed (`bb594c7e`). Model `flux`.** `Flux.train!(loss, model, data, opt)` calls `loss(model, x, y)`, but the loss was `loss(X, y)` over globals, so training failed. It is now the explicit `loss(m, X, y)`.
2. **Wrong, fixed (same commit). Action `hidden-heatmap` (Lux).** It ran a freshly initialised recurrence rather than the model's parameters; it now uses `ps.layer_1` and `st.layer_1`.
3. **Questionable.**
   - The Lux branch never trains, so every Lux action shows an untrained network.
   - `Flux.params` is set and never used.
   - The LSTM/GRU comparisons count parameters only.
   - Cells outside the listed set are not trained in the Flux branch.

   The Flux branch's Zygote use is already tracked.

**Proposal (thin).** The panel should answer: does a lighter gated cell (MGU, one gate) learn long dependencies as well as a GRU or LSTM with the same parameter budget? Use the adding problem or a copy task at sequence lengths of 20, 50 and 100, which have known difficulty. Train each cell to the same budget of updates, and plot validation MSE against sequence length and against parameter count. Add the gradient norm with respect to early inputs, which shows vanishing gradients directly. Train the Lux branch with Enzyme so that both branches are comparable.

### rng: Random Numbers Generation
