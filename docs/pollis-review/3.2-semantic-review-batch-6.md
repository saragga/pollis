# 3.2 Semantic review of the code examples, batch 6

Task 3.2 of the Pollis Polish Roadmap. Batch 6 is files 121 to 144 of `LC_ALL=C ls src/vs/workbench/contrib/model/browser/webviews/*.toml`, from `mcmc` to `node`. All 24 panels were reviewed.

The code was read as `node build/pollis/extractCodeExamples.ts` renders it (`.build/code-examples/<id>/<model>.jl`), covering the default code of every model and every Next Steps action, with each input at its default. No Julia was run; task 3.4 runs the code. Wikis and notebooks are out of scope. Verdicts, finding ratings and the "fixed" rule follow the batch 1 report (`3.2-semantic-review-batch-1.md`). A panel with a finding rated wrong is rated at least questionable, even when that finding is fixed here.

Where a finding depends on a package's API or conventions, I checked the package's source or documentation on GitHub. This covers MultilevelEstimators.jl, GraphsFlows.jl and NetworkDynamics.jl, and each such finding says so.

Items already tracked elsewhere are not repeated: postfix transposes, `bert` token attribution, `rl` Zygote, the `kgds`/`diff` mentions and `rxinfer`'s `gaussian_model`.

## Cross-cutting findings

- **U1. Defaults that switch the feature off (again).** This is the same pattern as Z1 in batch 3 and W1 in batch 4.
  - `mcmc`'s Turing model never used its data, so the samplers returned the prior (fixed).
  - `netdyn`'s cascades started with no node over capacity, so every cascade had size 0 (fixed).
  - `mpnlp`'s "nonconvex" objective was convex, so multi-start and local-against-global showed nothing (fixed).
  - `net`'s small-world graph was a degree-2 ring with zero clustering (fixed).
  - `mpsos`'s polynomial is exact at the first relaxation, so the hierarchy plot is flat.

  A reviewer can catch these by asking of each action: on the default data, could the result have come out otherwise?
- **U2. Package APIs that are invented or out of date.**
  - `mlmc` is written against functions MultilevelEstimators.jl does not have, which I checked against its source (not fixable locally).
  - `netdyn` used a NetworkDynamics edge signature that makes the coupling a dynamic state (fixed, following the current documentation).
  - `netflow` called `mincost_flow` with the wrong arguments (fixed).
  - `nntsf` uses Flux's implicit `params` API, removed in Flux 0.15.
- **U3. Library conventions misread.**
  - GraphsFlows returns an antisymmetric flow matrix, so a plain `sum` of it is 0 (`netflow`, fixed).
  - AdvancedHMC keeps warm-up draws unless `drop_warmup=true` (`mcmc`, fixed).
  - Graphs.jl's `watts_strogatz` rounds an odd k down (`net`, fixed).
  - NetworkDynamics' edge output goes to the destination, which reverses the sign of the coupling (`netdyn`, fixed).
- **U4. Input names that collide with template names.** `nlls`'s model-expression input was called `model` (fixed by renaming it to `fmodel`). This closes W3 from batch 4.
- **U5. In-sample comparisons.** In each case the flexible model wins by construction:
  - `nf` compares with its Gaussian baseline in-sample;
  - `nntsf` does all its evaluation in-sample;
  - `node` compares with its linear ODE baseline in-sample;
  - `mcmc` checks R-hat on a single chain.
- **U6. Zygote.** `nf`, `nntsf` and `node` differentiate with Zygote (`Flux.train!`, `AutoZygote`, `ZygoteVJP`), against the house rule of Enzyme for reverse mode (as W6 in batch 4).
- **U7. Actions that mutate the shared model.** Solver comparisons and parametric sweeps in `mpcone`, `mpsdp`, `mpsos` and `mpnlp` leave the next action a changed model: a new optimizer, a new right-hand side, deleted constraints or new start values.
- **U8. Non-ASCII in code.** `nf` uses the `÷` operator (in the `nsf` and `realnvp` models). As with `kgm` in batch 5, this is left for the task 3.3 sweep.

## Panel reviews

### mcmc: Markov Chain Monte Carlo

**Wrong, adequate.** NUTS and random-walk MH through Turing, plus hand-configured AdvancedHMC. Actions include traces, histograms, corner plots, R-hat, ESS, autocorrelation, posterior means and intervals, posterior predictive, WAIC/LOO, ESS per second and HPD.

1. **Wrong, fixed (`c722589f`). Models `nuts` and `mh`.** The default `@model` body `mu ~ Normal(0, 1); x ~ Normal(mu, 1)` never used `data`: `x` was a free parameter, so both samplers returned the prior (U1). The body is now `mu ~ Normal(0, 10); for i in eachindex(data); data[i] ~ Normal(mu, 1); end`, and the tooltip explains the rule. The posterior predictive `model(missing)` became `model(fill(missing, length(data)))`.
2. **Wrong, fixed (same commit). Model `hmc`.** AdvancedHMC's `sample(..., n, adaptor, n_adapts)` returns the adaptation draws unless `drop_warmup=true`, so the chain and every diagnostic included warm-up. The call now draws n + 500 and drops the 500.
3. **Questionable.** Every model runs one chain, so the "Gelman-Rubin R-hat" is at best split R-hat. Run four chains (`MCMCThreads()`).
4. **Questionable. Model `hmc`.** Several actions do not apply to this model:
   - the predictive, WAIC and LOO actions call `model(data)`, which the HMC branch does not define;
   - `chain.info[:elapsed]` does not exist for a `Chains` built by hand;
   - `waic` is not a ParetoSmooth export as far as I know (its Turing entry point is `psis_loo(model, chain)`).
5. **Questionable.** The HMC target is a standard normal, which needs nothing HMC offers; a correlated or funnel target would. The panel has three samplers but never compares them on one model. `data` is undefined.

### mdp: Single-Agent Decision Processes

**Sound, rich.** A lost-sales inventory MDP solved by value iteration: Poisson demand with the tail lumped correctly, and an expected-sales reward. The Tiger POMDP (standard -1/-100/+10 rewards, 0.85 accuracy) is solved by QMDP and compared with SARSOP and POMCP, with Bayes belief updates and alpha vectors. A semi-Markov maintenance model with duration-dependent discounting is compared with a constant-discount policy. Actions include Bellman residuals, Monte Carlo return against V, MCTS against VI and a myopic newsvendor baseline.

1. **Questionable. Action `mc-return` (POMDP).** It compares the simulated return with QMDP's V(0.5), which is an upper bound (QMDP assumes the state is revealed after one step). The gap is expected and should be explained as such.
2. **Questionable. Action `mcts-lookahead` (SMDP).** The reward rate divides by the requested number of periods, while the last action can run past them.

### mlmc: Multilevel Monte Carlo

**Wrong, thin.**

1. **Wrong, not local.** The API is not MultilevelEstimators.jl's. I checked this against its source:
   - it exports `Level`, `Index`, `ML`, `SL`, `TD`, `AD`, `U`, `MC`, `QMC`, `Normal`, `Uniform`, `LatticeRule32`, `Estimator`, `mean`, `var`, `History` and `run`;
   - the constructor is `Estimator(ML(), MC(), sample_fn, distributions; ...)`;
   - `run(estimator, tol)` returns a `History`.

   `MLMC()`, `MLQMC()`, `GaussianSampler`, `NumberOfLevels=`, `MSE=`, `mse`, `varest`, `cost`, `nb_of_levels`, `nb_of_samples`, `total_work` and `run(estimator; MSE=...)` do not exist. No default code or action runs (U2).
2. **Wrong.** The estimand is degenerate. `sample_fn` returns sin(2^-l x) itself, not the pair (dQ, Q) with dQ = Q_l - Q_{l-1} that its comment promises and the package requires. For X ~ N(0, 1), E[sin(cX)] = 0 at every level. So every level mean is 0, the "weak convergence rate alpha" is a regression on noise, and cost does not grow with level (gamma is about 0). The complexity check therefore says nothing.
3. **Questionable. Action `cost-forecast`.** "x10 for a 10x tighter MSE" assumes the eps^-2 regime without saying so. The MSE decomposition by subtraction assumes the package reports a bias estimate.

**Proposal (thin).** The panel should answer one question: how much cheaper is MLMC than plain MC for the same accuracy, and why? Use a hierarchy whose levels really get finer. For example, Q_l = midpoint rule with 2^l points for the integral from 0 to 1 of exp(X t) dt, with X ~ N(0, 1). The exact mean is the integral from 0 to 1 of e^(t^2/2) dt = 1.194958, and the rates are alpha = beta = 2 and gamma = 1. A second option is Euler-Maruyama for a GBM option payoff with 2^l steps, which has a Black-Scholes answer. The sample function should return (dQ, Q), using the same random input on both levels. Then run `run(estimator, tol)` for MC and ML. Read the level variances, costs and sample counts from the `History`, plot variance and mean decay on a log2 scale against level, and compare total cost at equal RMSE with the exact value as the check.

### mm: Mixed-Effects Models

1. **Wrong, fixed (`f3905ed5`). Action `lr-test`.** It compared the model with an LMM of the same formula. For the LMM that is the same model; for the GLMM the two are not nested. The restricted model is now the same fixed effects without random effects (`lm`/`glm`, with the GLMM's family and link), and the boundary caveat is stated.
2. **Wrong, fixed (same commit). Action `icc`.** It used `model.sigma`, which a Bernoulli GLMM does not have. It now uses the latent logistic variance pi^2/3; that is valid for the logit link only, which is stated.
3. **Questionable. Action `caterpillar`.** The "caterpillar plot with prediction intervals" draws no intervals (`condVar` exists, and `lmm` in batch 5 does this right).
4. **Questionable.** For a binary GLMM, fitted-against-observed and raw residuals-against-fitted are uninformative; use binned or randomised quantile residuals. The LRT formula is fixed at `y ~ x1 + x2` while the model uses the `formula` input. The panel overlaps heavily with `lmm` and `glmm`.

### mmn: Market Microstructure Noise

**Sound, rich.** The simulated log-price has time-varying volatility s(t) = 0.2(1 + 0.5 sin 2 pi t) plus i.i.d. noise with sd 0.005, about 1.5 times the per-tick diffusion sd, so the noise matters. Volatility is estimated bin by bin by FFBS Gibbs sampling (MicrostructureNoise.jl; its Greek keywords are built with `Symbol(Char(...))`, as policy requires). Actions include:
- a credible band against the true curve and the bounce-back in returns;
- traces, acceptance and mixing;
- the noise level and noise-to-signal ratio;
- integrated variance against its true value;
- realised variance at 1-, 10- and 50-tick sampling, which shows the noise bias;
- a refit that ignores the noise, and band coverage.

1. **Questionable. Action `coverage`.** It compares the band with s at the bin midpoint rather than the bin average of s^2; the difference is small with 40 bins. The bands are marginal, so joint coverage of all 40 bins is well below 90% and should not be expected.

### mopt: Optimization on Riemannian Manifolds

**Questionable, rich.** The Rayleigh quotient on the sphere, solved with Manopt's gradient descent, conjugate gradient, L-BFGS and trust regions. Actions include cost and gradient traces, distance to the solution (the rate), a finite-difference gradient check along geodesics, the stopping reason, restarts, a warm start, a solver comparison, budget and tolerance studies, eigmin(A) as the known answer, and an algorithm guide.

1. **Wrong, fixed (`9dc08d37`). Action `geodesic-distance`.** `path = [p0; res.iterates]` spliced p0's coordinates in as separate elements, so the path length summed distances between numbers and points. It is now `[[p0]; res.iterates]`.
2. **Questionable. Action `multiple-restarts`.** It looks for "other local minima", but the Rayleigh quotient on the sphere has none: every other critical point is a saddle. That is the lesson to state.
3. **Questionable. Action `algorithm-guide`.** Trust regions with a finite-difference Hessian approximation do not converge "quadratically", as the guide says. Solver timing includes compilation.

### mpc: Model Predictive Control

**Sound, rich.** Two examples:
- **Linear MPC** on a first-order plant. The gain is 2, so the setpoint of 1 needs u = 0.5, inside the +/-1.5 bounds.
- **Nonlinear MPC** swinging a pendulum up to 180 degrees; this is ModelPredictiveControl's manual example. The largest torque, 20.8 x 1.5 = 31.2, exceeds gravity's 24.5, so the swing-up is feasible.

Actions include:
- closed-loop and open-loop step responses;
- saturation and overshoot;
- solve time per step, with the first solve excluded;
- an input disturbance with offset-free estimation;
- 20% gain mismatch;
- a horizon sweep;
- an alternative controller (ExplicitMPC, or a linearised LinMPC);
- the move-weight trade-off and the receding-horizon plan.

1. **Questionable. Action `alternative-controller` (nonlinear).** `linearize(model)` linearises at the default operating point (hanging down, x = 0), not at the upright setpoint. The description "linearised at the operating point" should say which point, since the result depends on it.

### mpcone: Convex and Conic Programming

**Sound, rich.** Conic programming with Clarabel:
- a projection QP;
- maximum entropy under a mean constraint via exponential cones (u <= -x log x, encoded correctly);
- p-norm regression via power cones (`[e; 1; r] in PowerCone(1/p)` gives e >= |r|^p, which is correct);
- norm-constrained least squares via second-order cones.

Actions include a feasibility report, the duality gap, cone duals, cone membership by `distance_to_set`, parametric sweeps, a solver comparison and baselines (uniform entropy log n, OLS, LAD).

1. **Questionable (U7).** Several actions leave the shared model changed for the next action: the sweep leaves the last grid value in place, `solver-compare` leaves SCS as the optimizer, and `baseline` deletes the constraint (a comment says so).
2. **Questionable. Model `expcone`.** The baseline could state that the maximum-entropy solution is the exponential tilt x_i proportional to exp(lambda i), with lambda the dual of the mean constraint.

### mpec: Mathematical Programming with Equilibrium Constraints

**Sound, rich.** A Stackelberg leader (cost 1) faces two Cournot followers (costs 1 and 2) under inverse demand 10 - Q. The followers' first-order conditions are complementarity constraints (f_k = c_k + Q + y_k - 10, which is correct). The problem is solved three ways: implicit programming with PATH on a grid, Scholtes regularisation and a penalty. Actions include complementarity and one-sided stationarity checks, the relaxed bound, a parametric cap, a method comparison, the value of commitment against Nash, and the active pairs.

The results can be checked by hand:
- The followers give Q = (17 + x)/3, so the leader's profit is x(10 - x)/3.
- That is maximised at x = 5, with profit 25/3, F = -8.333 and y = (5/3, 2/3).
- Simultaneous Cournot gives the leader 2.5 and profit 6.25.
- The value of commitment is therefore 2.083.

1. **Questionable.** Print these closed forms as the check. `solve_imp`'s grid of 201 points on [0, 10] happens to contain x = 5 exactly; with other data, state the grid error (step 0.05) or refine the grid.

### mpm: Multi-Objective Optimisation Performance Metrics

**Sound, rich.** Performance metrics on NSGA-II and SPEA2 fronts for ZDT1, whose true front is known:
- hypervolume with a shared reference point;
- GD and IGD;
- additive epsilon (the max over reference points of the min over the front of max_k (a_k - r_k), which is correct);
- Schott spacing.

Each metric is drawn on the front, over generations and point by point. The panel also shows subsample sensitivity, a two-front comparison, set coverage in both directions, and a guide to what each metric rewards.

1. **Questionable. Action `compare-fronts`.** It declares a winner from a single seed of each algorithm. Stochastic optimisers need several seeds and a spread, or attainment surfaces.
2. **Questionable.** The reference point is derived from the fronts being compared, so hypervolume values change when a front is added. Say so.

### mpnlp: Nonlinear Programming

**Questionable, rich.** NLP (Ipopt), global NLP (EAGO) and MINLP with a cardinality limit (SCIP, Juniper) on one model. Actions include contours, a feasibility report, a multi-start histogram, solver statistics, shadow prices, a bound sweep, a solver comparison, local-against-global and integer-against-relaxation gaps, KKT complementarity and constraint activity.

1. **Wrong, fixed (`3e30032d`). Input `obj`.** The default `sum((x .- 1) .^ 2) + prod(x[1:2])` is convex: its Hessian eigenvalues are 1 and 3. It has one minimum, 0.667 at (2/3, 2/3, 1, 1, 1), so Ipopt is already global, and the multi-start and local-against-global actions showed nothing (U1). The new default, `sum((x .- 1) .^ 2) + 3 * x[1] * x[2] + x[1]`, has two local minima in the feasible ball, about -0.54 and 1.69. I checked this with projected gradient descent from 200 starts, not with Julia.
2. **Questionable. Model `minlp`.** The big-M uses the box [-5, 5], although the ball already bounds |x_i| <= 2; M = 2 is tighter for SCIP. Multi-start leaves changed start values on the shared model (U7).

### mpsdp: Semidefinite Programming

**Sound, rich.** Two models:
- **A basic SDP:** min tr(CX) subject to tr X = 1. Its optimum is lambda_min(C), which is stated as the baseline.
- **The Goemans-Williamson max-cut relaxation:** the Laplacian cut is x'Lx/4, node vectors come from a Cholesky factorisation, and rounding uses random hyperplanes. Brute force for n <= 20 fixes one node by symmetry, which is correct.

Actions include the heatmap, spectrum and rank (tightness), feasibility, the duality gap, the dual PSD matrix with tr(XS) complementarity, sweeps, a solver comparison and a leading-eigenvector partition.

1. **Questionable.** The 0.878 guarantee is on the expected cut of one random hyperplane relative to the SDP bound. The comment "ratio >= 0.878 in expectation" sits on the best of 100 trials, which says more than that.
2. **Questionable.** With n = 6 the relaxation is often tight; a graph with n = 30 shows the gap. `solver-compare` leaves the model on Hypatia (U7).

### mpsos: Polynomial Programming

**Sound, rich.** An SOS certificate of non-negativity and Putinar/Lasserre lower bounds on a ball. The polynomial is p = x1^4 + x2^4 - x1^2 - x2^2 + 1, with true minimum 0.5 at (+/-1/sqrt 2, +/-1/sqrt 2). Actions include:
- the Gram matrix with a PSD check and the identity residual;
- contours;
- the hierarchy over degrees;
- minimiser extraction from the moment matrix;
- the SOS bound against sampling (correctly described as an upper bound);
- the explicit squares and the SOS multipliers.

1. **Questionable (U1). Action `tighten`.** The default polynomial is separable, and the first relaxation is already exact, so "Tighten Relaxation" plots a flat line. The Motzkin polynomial is non-negative but not SOS, so it would show both the failure of plain SOS and the climb of the hierarchy. `solver-compare` leaves SCS on the model (U7).

### net: Network Analysis

**Wrong, adequate.**

The random baseline is usually disconnected, so the small-world index was garbage. It is now the mean over all reachable pairs, in eight places.

The lattice now has k neighbours per side, giving mean degree 2k, which matches the scale-free graph. The tooltip is updated, and the ER baselines use p = 2k/(N - 1).

### netdyn: Network Dynamics

**Wrong, adequate.**

1. **Wrong, fixed (`c4dbe543`). Model `kuramoto` and four actions.** The edge was `EdgeModel(f=..., dim=1)` with `de = sin(theta_dst - theta_src)`. That makes the coupling a dynamic edge state, so vertices summed integrated sines. The sign also pushes phases apart, because the edge output goes to the destination. The six-argument signature and the `coupling=` keyword predate the current API (U2, U3). The network is now built as the NetworkDynamics documentation shows: a static `AntiSymmetric` output K sin(theta_src - theta_dst), and vertices `f(dv, v, esum, p, t)` with dtheta = omega_i + esum.
2. **Wrong, fixed (same commit). Model `cascade` and its actions.** Every cascade started from loads `rand() * 0.8` against capacity 1 and queued only nodes already over capacity, so no node ever failed. Every cascade, histogram and topology comparison showed 0 (U1). Each run now starts with one random failure, as the hub-attack action already did.
3. **Questionable. Action `critical-coupling`.** K_c = 2 std(omega)/lambda_2 is not a standard estimate. Dorfler and Bullo give sufficient conditions for phase locking in terms of lambda_2 and the spread of omega; the mean-field onset is about K_c(all-to-all) <k>/<k^2>. Label it a rough bound.
4. **Questionable. Actions `coupling-sweep` and `sync-state`.** With sigma = 0.1 and degrees of at least 3, K = 0.3 is far above the onset, so the sweep from 0 to 1.5 in steps of 0.05 shows r near 1 from its second point. Use a log grid from 0.001. The r thresholds of 0.85 and 0.4 are arbitrary. Every action redraws omega and the network.

### netflow: Network Flows

**Wrong, adequate.** I checked the following against GraphsFlows' source:
- `maximum_flow` defaults to push-relabel;
- it returns an antisymmetric flow matrix (`push_flow!` does F[u,v] += f; F[v,u] -= f);
- `mincost_flow(g, node_demand, capacity, cost, optimizer)` returns only the flow matrix;
- no s-t `mincut` is exported.

1. **Wrong, fixed (`fa96d1ca`). Action `network-utilisation`.** Utilisation `sum(flow_mat)` / capacity was 0 by construction (U3); it now uses the positive part.
2. **Wrong, fixed (same commit). Action `flow-conservation`.** The check compared sums that included the negative entries; it now uses the positive parts.
3. **Wrong, fixed (same commit). Model `mincut` and action `bottleneck-edges`.** The "minimum cut" was every saturated edge, which is a superset of the cut. The `mincut` model now finds the true cut by residual reachability from the source and prints its capacity next to the max flow. The description of `bottleneck-edges` now says the saturated edges only contain the cut.
4. **Wrong, fixed (same commit). Model `mincost`.** It called `mincost_flow(g, cap, cost, demand)` and unpacked two results. It now uses the documented signature with HiGHS and computes cost = sum(F .* cost).
5. **Wrong, fixed (same commit). Model `maxflow`.** A comment said the algorithm was Dinic; it is push-relabel. The notebook description is fixed too. The model's "detail" text still says Dinic.
6. **Questionable.** 40 random arcs on 20 nodes give a mean out-degree of 2. This often leaves no path from node 1 to node 20 (max flow 0), or too little capacity for the 10-unit min-cost demand (an infeasible LP). Seed the graph and guarantee a path, as `ngo` does. Every action rebuilds its own random graph, and the `mincost` and `mincut` models get only max-flow actions.

### nf: Normalising Flows

**Sound, rich.** Three flows trained by maximum likelihood:
- **MAF with a hand-written MADE.** The masks check out: input k <= deg, hidden deg_out >= deg_in, output i > deg. The transform is z = (x - mu) e^-alpha with log det = -sum alpha.
- **RealNVP affine coupling,** with log det = sum s.
- **Neural spline flows** through Bijectors' `RationalQuadraticSpline`.

Actions include a loss curve, latent scatter and normality, held-out log-likelihood, densities of new points, the least likely samples, a Gaussian baseline, per-step log-determinants and a density slice.

1. **Questionable (U6).** `Flux.train!` differentiates with Zygote.
2. **Questionable (U5). Action `gaussian-baseline`.** The baseline is compared in-sample, where a flow with about 10^5 parameters always wins. Use `X_test` for both.
3. **Questionable (U8). Models `nsf` and `realnvp`.** `input_dim ÷ 2` is a non-ASCII operator in code.
4. **Questionable.** RealNVP's log-scale s is an unbounded linear output, which often diverges early; scaling it with tanh is the usual guard. `Dropout(0.0)` is a no-op. `X`, `X_test` and `X_new` are undefined.

### ngo: Network and Graph Optimisation

**Sound, rich.** Six network problems on one seeded random digraph, with a 1 -> n chain that guarantees reachability:
- Dijkstra shortest path;
- the min-max-regret robust path (the worst case puts the path's arcs at their upper bounds and all other arcs at their lower bounds, the correct characterisation);
- max flow (using the positive part of the antisymmetric flow correctly);
- a Kruskal spanning tree;
- max-weight bipartite matching;
- assignment by the Hungarian method.

Actions include validation of each solution's constraints and independent cross-checks: the LP relaxation of assignment is integral, and sampled scenarios never exceed the worst-case regret. Further actions add weight noise, edge removal, all-pairs distances, timing after warm-up, scaling, baselines and an algorithm guide.
