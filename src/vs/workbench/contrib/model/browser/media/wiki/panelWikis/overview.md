# Panel Documentation — Overview

## How Panel Documentation Is Organised
Each row of Panel Documentation is one panel or Compose page, under the heading of the menu that opens it, with its wikis listed beside it. The wikis are the same as those in the page's own Learn More. Click a wiki to read it.

## What the Written and Not Written Switch Shows
The switch shows either the wikis written or the ones not written yet, with **Show Written Wikis** and **Show Wikis Not Written** as its hovers, and the page counts how many of all the wikis are written. A wiki not written yet appears in a panel's Learn More as a stub saying **Not written yet**. When the search and the switch together leave nothing, the page says **No panel or wiki matches.**

## How the Factsheets in Panel Documentation Relate to Model Cards and Datasheets
Short structured documents for those who use a model or a dataset have a literature of their own. Model cards, from [Mitchell, Wu, Zaldivar, Barnes, Vasserman, Hutchinson, Spitzer, Raji and Gebru (2019)](#ref-MWZBV...2019a), state the context of a model's intended use, so as to minimise its use where it is not well suited. FactSheets, from [Arnold, Bellamy, Hind, Houde, Mehta, Mojsilović, Nair, Ramamurthy, Olteanu, Piorkowski, Reimer, Richards, Tsay and Varshney (2019)](#ref-ABHHM...2019a), take after suppliers' declarations of conformity and cover purpose, performance, safety, security and provenance. Datasheets, from [Gebru, Morgenstern, Vecchione, Vaughan, Wallach, Daumé III and Crawford (2021)](#ref-GMVVW...2021a), ease communication between those who create a dataset and those who use it. A Pollis Factsheet shares that aim for a panel or page: what it is for, and when to use it.

## Why the Wikis Listed in Panel Documentation Differ in Kind
A reader looking for a fact and a reader looking for a reason want different documents. Diátaxis, by [Procida (2026)](#ref-Pro2026a), separates four forms: tutorials, how-to guides, reference and explanation. A how-to guide addresses a real-world goal or problem, reference is technical description, and explanation gives context and background, answering why. Among the wikis that Panel Documentation lists, a Factsheet is mostly reference and an Overview mostly explanation, while tutorials fall to a panel's notebooks. Keeping each section to one form also makes it easier to find on its own.

## Why Software Documentation Goes Missing and What the Not Written Count Is For
[Aghajani, Nagy, Vega-Marquez, Linares-Vasquez, Moreno, Bavota and Lanza (2019)](#ref-ANVLM...2019a) read 878 documentation-related artifacts from mailing lists, Stack Overflow, issue repositories and pull requests, and built from them a taxonomy of documentation issues, finding that creating and maintaining documentation is often neglected. **Show Wikis Not Written** in Panel Documentation keeps that gap in view: a wiki missing is counted and listed, not simply absent.

## Documentation Written for Human Readers Alongside the Code
[Knuth (1984)](#ref-Knu1984a) introduced literate programming with WEB, at once a programming language and a documentation system, asking authors to think of explaining to human beings what they want a computer to do. [Parnas and Clements (1986)](#ref-PC1986a) accept that a real design never follows an ideal process, and still ask for the documentation such a process would have produced. Both views fit a panel's wikis, which ship with the panel's code and describe what the panel is, not the order in which it came to be.
